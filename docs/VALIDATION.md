# 第一版验证记录

2026-10-30。本仓库从原项目的离线交接工具思路整理而来，重新实现为平台无关的请求包；没有修改原项目代码，没有导入客户资料或已有凭据。

## 本机实际运行

- Node.js 25：5 个测试分组通过，包含标准 age 文件往返/错身份拒绝、Unicode/JSON/换行秘密往返、错私钥/任务/环境/版本、篡改、过期和大小上限、页面转义、完整 CLI 生成/加密/接收、拒绝覆盖与 Git 内输出、0600 文件权限及无明文回显。
- Chromium：6 个连续交互用例通过。Resend、Stripe、GitHub 的合成请求各跑一次本地 HTML → 粘贴 → 下载 → CLI 解密，以及过期拒绝；核对零 HTTP 请求、输入清空与准确下载文件名。未对真实客户使用这些工具。
- POSIX 真实伪终端：隐藏输入后准确解密，无秘密回显。验证时发现提示可能先于 raw 输入准备出现，已把提示移到终端隐藏模式就绪之后，再复跑通过。测试自身 EOF 循环也已修正。
- 定向缺陷注入：在临时副本移除响应版本检查、请求有效期检查，两处都被行为断言抓到；真实源码没有被修改。
- skill-creator 的 quick_validate 校验通过。它验证结构和元数据，不证明所有未来 agent 都会正确选权限。

## 核对的资料与人工复核

检查了 `SKILL.md`、`scripts/handoff.mjs`、README、平台参考、Resend 短例子、备用说明及全部测试代码。重点核对公开包没有私钥、接收端使用本机留存请求、输出不进入 Git、不覆盖已有文件、标签不等于供应商实际沙箱、有效期不等于撤销密钥。

文字上把“先选一种安全交接方式，再创建 Key”的分散叙述改为“确定用途 → 对方创建 → 选定渠道加密 → 交付密文 → 本机接收”；每次给老板的成稿只出现选中的一条顺序。API Key、账号邀请和测试邮箱分别解释，权限取值按平台区分。

平台资料来自各 reference 内链接的官方文档：Resend、Stripe、GitHub、age、1Password、Bitwarden。密码管理器只做文档核对，没有登录、生成真实分享链接或验收手机客户端。桌面浏览器通过不代表微信/iOS 附件能执行 HTML。

## 限制

这是使用标准 Node/Web Crypto 算法的第一版工程工具，未经过独立密码学审计。加密不能证明发送方身份，不能保护已经失陷的终端，也不能追回被复制的秘密。须通过已确认渠道核对文件和公钥指纹。

POSIX 权限检查不能代替 Windows ACL；Windows 的 Node CLI 和单元边界由远端 CI 单独验证。age 在没有安装的 CI 环境会明确跳过，不伪装成测试通过。没有独立新会话 agent 的行为实测，没有实际支付、邮件发送、客户账号变更或部署。

远端 CI 与实际提交由交付时核对；这里只记录已执行的检查，不预写“全部平台上线”。
